The `sessionId` query parameter is read only when the server enables resume (`transport.resume`), and only if it is 1–128 characters of `[A-Za-z0-9_-]`. It is not a credential: the server rejoins that conversation only if it belongs to the connection's authenticated user, and answers any other id — someone else's, one it never issued, or one its store no longer holds — with a fresh session exactly as if no id had been sent. With `transport.resume.latest`, a connect that sends no id rejoins the user's most recently active conversation instead, unless it sends `?new=1`, which starts a new one. No further `entry_delta` messages will be sent for this index (within the current streaming sequence).\n270\t\n271\t```json\n272\t{\n273\t  \"type\": \"entry_commit\",\n274\t  \"index\": 1\n275\t}\n276\t```\n277\t\n278\t| Field   | Type   | Description                  |\n279\t| ------- | ------ | ---------------------------- |\n280\t| `type`  | string | `\"entry_commit\"`             |\n281\t| `index` | number | Index of the entry to commit |\n282\t\n283\tSemantics:\n284\t\n285\t- The client MUST set `isStreaming` to `false` on the entry at the given index.\n286\t- After a commit, the entry's content is considered complete and stable.\n287\t\n288\t### 5.5 entry_skip\n289\t\n290\tNotifies the client that a session entry was created on the server and will never be sent. This happens under output suppression (see [tool-responses.md](../hal-engine-tool-responses/spec.md)): the server keeps the entry so the model retains context, and the client does not need it for display ([validated by: still records a suppressed reply in the session, so history keeps it](../../src/transport/ws/messageHandler.test.ts#L212)).\n291\t\n292\t```json\n293\t{\n294\t  \"type\": \"entry_skip\",\n295\t  \"index\": 3\n296\t}\n297\t```\n298\t\n299\t| Field   | Type   | Description                            |\n300\t| ------- | ------ | -------------------------------------- |\n301\t| `type`  | string | `\"entry_skip\"`                         |\n302\t| `index` | number | Server-side index of the skipped entry |\n303\t\n304\tSuppression can begin before or after the server has started sending a reply, and the two cases produce different messages. This distinction is the whole of the protocol here:\n305\t\n306\t- An entry **opened while suppression is already active** is announced with `entry_skip` and nothing else: no `entry_upsert`, no `entry_delta`, no `entry_commit` follows it ([validated by: skips rather than upserts a segment opened after suppression](../../src/transport/ws/messageHandler.test.ts#L204)).\n307\t- An entry **already sent before suppression began** cannot be skipped, because the client is displaying it. The server retracts it instead, by re-sending `entry_upsert` at the same index with the entry's `content` set to `\"\"`. The client renders an empty assistant entry as nothing, so the text disappears ([validated by: blanks an assistant entry that was already sent](../../src/transport/ws/messageHandler.test.ts#L181)).\n308\t- An entry **still streaming when suppression begins** is first committed as streamed so far, with `entry_commit`, and is from then on an entry already sent: an answer is retracted as above, a thought stays as the client saw it, and whatever the model writes next opens a new entry announced with `entry_skip` ([validated by: commits and retracts an answer still open when suppression begins, and skips what follows as a new entry](../../src/transport/ws/messageHandler.test.ts#L268), [validated by: commits a thought still open when suppression begins as the client saw it, and skips what follows](../../src/transport/ws/messageHandler.test.ts#L289)).\n309\t\n310\t#### Limits of retraction\n311\t\n312\t- Only assistant entries are ever retracted; a thinking entry is never blanked, even when it was sent before suppression began ([validated by: never blanks a thinking entry, only assistant ones](../../src/transport/ws/messageHandler.test.ts#L196)).\n313\t- Each sent entry is blanked once, so a second suppression in the same stream repeats nothing ([validated by: blanks each sent entry once, so a second suppression repeats nothing](../../src/transport/ws/messageHandler.test.ts#L230)).\n314\t- An entry the client only ever saw as `entry_skip` is never retracted, because nothing is displayed to retract ([validated by: does not resurrect an entry the client only ever saw skipped](../../src/transport/ws/messageHandler.test.ts#L222)).\n315\t\n316\tSemantics:\n317\t\n318\t- The client MUST track skipped indices to adjust subsequent `entry_upsert`, `entry_delta`, and `entry_commit` indices. Server indices diverge from the client array when entries are skipped.\n319\t- The adjustment formula: for any incoming index, subtract the count of skipped indices that are less than or equal to it. This maps the server index to the correct client array position.\n320\t- A retracted entry is NOT a skipped entry and MUST NOT be counted in that adjustment: it still occupies its position in the client array.\n321\t- Skipped indices are always monotonically increasing within a session.\n322\t- The client MUST reset its tracked skipped indices on disconnect/reconnect.\n323\t\n324\t### 5.6 error\n325\t\n326\tReports an error condition. The connection remains open unless the error is fatal.\n327\t\n328\t```json\n329\t{\n330\t  \"type\": \"error\",\n331\t  \"code\": \"INVALID_MESSAGE\",\n332\t  \"message\": \"Message content cannot be empty\"\n333\t}\n334\t```\n335\t\n336\t| Field     | Type   | Description           |\n337\t| --------- | ------ | --------------------- |\n338\t| `type`    | string | `\"error\"`             |\n339\t| `code`    | string | Machine-readable code |\n340\t| `message` | string | Human-readable detail |\n341\t\n342\tDefined error codes:\n343\t\n344\t| Code              | Description                                                       |\n345\t| ----------------- | ----------------------------------------------------------------- |\n346\t| `INVALID_MESSAGE` | Message failed validation (missing fields, empty content, length) |\n347\t| `INVALID_FORMAT`  | Message body is not valid JSON                                    |\n348\t| `RATE_LIMITED`    | AI provider returned a rate limit error                           |\n349\t| `SERVER_ERROR`    | Unexpected server error during message processing                 |\n350\t\n351\tSemantics:\n352\t\n353\t- A message the server cannot parse into a known type is answered with `INVALID_MESSAGE`, and no message stream is started for it ([validated by: rejects an unparseable message and never starts a stream](../../src/transport/ws/messageHandler.test.ts#L72)).\n354\t- A rate limit reported by the AI provider is surfaced as `RATE_LIMITED`, which tells the client the same request is worth retrying ([validated by: tells the client to retry when the provider is rate limited](../../src/transport/ws/messageHandler.test.ts#L312)).\n355\t- Any other failure raised while processing a message is reported as `SERVER_ERROR` ([validated by: reports any other failure as a server error](../../src/transport/ws/messageHandler.test.ts#L321)).\n356\t\n357\t### 5.7 pong\n358\t\n359\tResponse to a client `ping`. The server MUST echo the client's timestamp without modification ([validated by: answers a ping with the timestamp it was given](../../src/transport/ws/messageHandler.test.ts#L82)).\n360\t\n361\t```json\n362\t{\n363\t  \"type\": \"pong\",\n364\t  \"timestamp\": 1705312200000\n365\t}\n366\t```\n367\t\n368\t| Field       | Type   | Description                             |\n369\t| ----------- | ------ | --------------------------------------- |\n370\t| `type`      | string | `\"pong\"`                                |\n371\t| `timestamp` | number | Echoed from the client's `ping` message |\n372\t\n373\t### 5.8 stream_end\n374\t\n375\tSignals that the server has finished processing a user message. Sent exactly once for every `user_message` the server receives, after all `entry_commit` messages have been sent, whether the run succeeded or failed.\n376\t\n377\t```json\n378\t{\n379\t  \"type\": \"stream_end\"\n380\t}\n381\t```\n382\t\n383\t| Field  | Type   | Description    |\n384\t| ------ | ------ | -------------- |\n385\t| `type` | string | `\"stream_end\"` |\n386\t\n387\tSemantics:\n388\t\n389\t- The server MUST send `stream_end` after every `user_message` it receives, including streams where output was suppressed (see [tool-responses.md](../hal-engine-tool-responses/spec.md)), streams that failed after an `error` frame, and a `user_message` that failed validation ([single-terminal-frame](../hal-engine-single-terminal-frame/spec.md)). The one exception is a turn whose socket closes first: it is abandoned, and nothing more is sent ([abandon-on-close](../hal-engine-abandon-on-close/spec.md)).\n390\t- `stream_end` follows every stream even after an error: a failed run sends its `error` frame first and `stream_end` last.\n391\t- An `error` frame does not by itself end a stream. It is advisory: it may concern the run in flight or an unrelated frame, such as a malformed `ping`.\n392\t- The client SHOULD use this message to clear any \"processing\" or \"loading\" indicators.\n393\t- The client MUST treat a run as complete only at `stream_end` or when the socket closes. Unparseable JSON is the one frame answered with `INVALID_FORMAT` and no `stream_end`, because the server cannot tell what it was meant to be; for it the client falls back on the socket closing.\n394\t\n395\t## 6. SessionEntry Objects\n396\t\n397\tA SessionEntry represents a single piece of content in the conversation. Every entry has a `role` field that determines its shape. The `role` acts as a discriminant for the union type.\n398\t\n399\t### 6.1 UserEntry\n400\t\n401\tA message authored by the user.\n402\t\n403\t```json\n404\t{\n405\t  \"role\": \"user\",\n406\t  \"content\": \"What is the weather in Berlin?\",\n407\t  \"timestamp\": \"2026-01-15T14:30:00Z\"\n408\t}\n409\t```\n410\t\n411\t| Field       | Type   | Description       |\n412\t| ----------- | ------ | ----------------- |\n413\t| `role`      | string | `\"user\"`          |\n414\t| `content`   | string | The message text  |\n415\t| `timestamp` | string | ISO 8601 datetime |\n416\t\n417\t### 6.2 AssistantEntry\n418\t\n419\tA response generated by the AI model. Content is delivered incrementally via `entry_delta` messages while `isStreaming` is `true`.\n420\t\n421\t```json\n422\t{\n423\t  \"role\": \"assistant\",\n424\t  \"content\": \"Berlin currently has a temperature of 18 degrees Celsius.\",\n425\t  \"timestamp\": \"2026-01-15T14:30:01Z\",\n426\t  \"isStreaming\": false\n427\t}\n428\t```\n429\t\n430\t| Field         | Type    | Description                                                                                                                             |\n431\t| ------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------- |\n432\t| `role`        | string  | `\"assistant\"`                                                                                                                           |\n433\t| `content`     | string  | Markdown text, built incrementally by deltas                                                                                            |\n434\t| `timestamp`   | string  | ISO 8601 datetime                                                                                                                       |\n435\t| `isStreaming` | boolean | `true` while deltas are arriving                                                                                                        |\n436\t| `truncated`   | `true`  | Optional. Present only when the run ended before this entry finished, or when a resume replays it still streaming; see § 7.1 and § 11.3 |\n437\t\n438\t### 6.3 ThinkingEntry\n439\t\n440\tInternal AI reasoning, separated from user-facing content by the server's thinking tag parser. The client SHOULD render this as a collapsible section.\n441\t\n442\t```json\n443\t{\n444\t  \"role\": \"thinking\",\n445\t  \"content\": \"I should look up the weather for Berlin using the get_weather tool.\",\n446\t  \"isStreaming\": false\n447\t}\n448\t```\n449\t\n450\t| Field         | Type    | Description                                                                                                                             |\n451\t| ------------- | ------- | --------------------------------------------------------------------------------------------------------------------------------------- |\n452\t| `role`        | string  | `\"thinking\"`                                                                                                                            |\n453\t| `content`     | string  | Reasoning text, built incrementally                                                                                                     |\n454\t| `isStreaming` | boolean | `true` while deltas are arriving                                                                                                        |\n455\t| `truncated`   | `true`  | Optional. Present only when the run ended before this entry finished, or when a resume replays it still streaming; see § 7.1 and § 11.3 |\n456\t\n457\tNote: ThinkingEntry does not include a `timestamp` field.\n458\t\n459\t### 6.4 ToolEntry\n460\t\n461\tA tool invocation requested by the AI model. The server executes the tool and feeds the result back to the model. The client SHOULD render tool entries with the tool name, parameters, and an activity indicator.\n462\t\n463\t```json\n464\t{\n465\t  \"role\": \"tool\",\n466\t  \"toolName\": \"get_weather\",\n467\t  \"toolInput\": {\n468\t    \"location\": \"Berlin\",\n469\t    \"units\": \"celsius\"\n470\t  },\n471\t  \"timestamp\": \"2026-01-15T14:30:01Z\"\n472\t}\n473\t```\n474\t\n475\t| Field       | Type   | Description                        |\n476\t| ----------- | ------ | ---------------------------------- |\n477\t| `role`      | string | `\"tool\"`                           |\n478\t| `toolName`  | string | Registered tool name               |\n479\t| `toolInput` | object | Key-value pairs passed to the tool |\n480\t| `timestamp` | string | ISO 8601 datetime                  |\n481\t\n482\tNote: ToolEntry does not participate in the delta/commit cycle. It is delivered as a single `entry_upsert`.\n483\t\n484\t## 7. Entry Lifecycle\n485\t\n486\tEntries follow one of two lifecycles depending on whether they support streaming.\n487\t\n488\t### 7.1 Streaming Entries (assistant, thinking)\n489\t\n490\t```text\n491\tentry_upsert  -->  entry_delta (0..N)  -->  entry_commit\n492\t   |                    |                       |\n493\t   |  isStreaming=true  |  content grows        |  isStreaming=false\n494\t   |  content=\"\"        |  via concatenation    |  content is final\n495\t```\n496\t\n497\t1. The server sends `entry_upsert` with `isStreaming: true` and an empty `content`.\n498\t2. The server sends zero or more `entry_delta` messages. The client MUST concatenate each `delta` to the entry's `content`.\n499\t3. The server sends `entry_commit`. The client MUST set `isStreaming` to `false`, matching the committed entry the server keeps in the session. No further deltas will arrive for this entry ([validated by: leaves the committed assistant entry in the session, no longer streaming](../../src/transport/ws/messageHandler.test.ts#L106)).\n500\t4
