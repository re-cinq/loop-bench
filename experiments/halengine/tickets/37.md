# Validate tool input against the registered inputSchema

Issue: re-cinq/HALEngine#37
Labels: priority:medium, type:feature, size:M, area:tools, epic:extension-points

Part of #35

## Why

`ToolRegistry.execute` looks a tool up, logs the input's key names, and calls the executor
without ever checking the declared `inputSchema` (`src/orchestration/tools/registry.ts`).
Every tool declares a JSON Schema (`src/types/ai.ts`) that is handed verbatim to both
providers, but nothing validates what comes back from the model. The shipped example shows the
shape of the problem: `example/weather-tool.ts` declares `location` as a required string, then
casts and defaults it (`(input.location as string) || 'Unknown'`) with a comment warning the reader
that `inputSchema` shapes what the model sends but does not enforce it. That is the careful version,
written by the people who wrote the engine — and it still answers a malformed call with a
confidently formatted forecast for `'Unknown'` rather than telling the model it got the call wrong.

The registry currently pushes this check onto each tool's own executor, leaving every consumer
to implement it itself — differently each time, or not at all. A tool that receives unexpected input must fail
in one predictable, known way before the rest of this epic's tool work can be built on top
of it.

## What to do

Validate `input` against the resolved tool definition's `inputSchema` inside
`ToolRegistry.execute`, before the executor runs, using a JSON Schema validator (`ajv`
unless the build proves otherwise) added to `dependencies` — not a second, hand-written
schema in a different format, since the schema already has to match what is handed to the
providers.

Compile a static tool's schema once at `register` time so a broken schema fails at startup,
not mid-conversation; a schema produced by a function-valued `ToolDefinitionSource`
resolves and compiles per call, cached by the resolved schema object.

A rejection returns a `ToolResponse` (`{result: '<what was wrong>'}`) rather than throwing,
so a malformed call becomes something the model can read and correct within the existing
`DEFAULT_MAX_TOOL_ROUNDS = 5` budget, instead of ending the whole conversation with a
generic transport error. Validation enforces `required`, declared types and `enum` only —
it does not inject `additionalProperties: false`, coerce types, or apply defaults, and
there is no opt-out flag.

Update `docs/adding-a-tool.md`, `README.md` and `.specify/spec.md` to match.

## Tech notes

Today's `throw` in `registry.ts` propagates through the orchestrator's tool-call
`Promise.all`, out of the processing loop's `try`, fires `onError`, and reaches the
WebSocket error handler, which sends a generic "Failed to process message" and never sends
the stream-end frame. That end-to-end path is why a rejection has to be a returned
`ToolResponse` instead of a throw.

Deliberately out of scope: the `Unknown tool: <name>` throw stays as-is — the same failure
class handled the opposite way, which is an intentional split, but changing it affects
direct callers and is tracked as *Return an unknown tool name to the model instead of
throwing*. Also out of scope: validating tool *output*; hallucination detection and an
evaluation harness; per-tool authorization — a schema-valid call for someone else's data is still
valid, and authorization is a separate `ToolContext` boundary concern that no issue in this epic
owns (*Let a consumer decline a tool call through a `beforeToolCall` hook* is a veto seam, not an
authorization model); retry, timeout
and rate limiting around tool execution; and any actual tool implementation, which is
written against this contract later.
