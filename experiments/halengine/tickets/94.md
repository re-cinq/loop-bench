# Run onError and afterSession when beforeSession throws

Issue: re-cinq/HALEngine#94
Labels: priority:medium, type:bug, size:S, area:api

## Why

`beforeSession` is awaited before the `try` block opens, so a throw from it escapes before the `catch` and `finally` exist. Neither `onError` nor `afterSession` runs.

That breaks the guarantee the hook names imply. A deployer who allocates something in `beforeSession` — a span, a database handle, a rate-limit token — and releases it in `afterSession` leaks it on exactly the path where the allocation failed, and learns nothing from `onError` because it never fires. The failure is silent in the engine and visible only as an unexplained rejection at the caller.

Recorded as measured behaviour in `specs/hal-engine-config-hooks/spec.md` by HALEngine#83, which scoped itself to specifying the seam rather than changing it, and raised again by the reviewer on that PR. The spec notes this property is owned by no issue in the epic; this is that issue.

## What to do

Move the `beforeSession` call inside the `try`, so a throw from it reaches the same `catch` and `finally` as any other failure in the turn, and decide one question explicitly: whether `afterSession` running after a failed `beforeSession` is what a deployer wants, or whether it needs to know the session never started. Record the answer in the spec either way, because a cleanup hook that cannot tell "never allocated" from "allocated and finished" is a new trap for the same reader.

## Acceptance criteria

- [ ] A `beforeSession` that throws still reaches the caller as a rejection, unchanged from today
- [ ] `onError` fires for that throw, with the same argument shape as any other orchestrator failure
- [ ] `afterSession` fires for that throw, and the spec states what a hook can assume about how much of the turn happened
- [ ] A non-throwing `beforeSession` behaves exactly as today, pinned by the existing tests remaining unedited
- [ ] `specs/hal-engine-config-hooks/spec.md` replaces its recorded-flaw line with the new guarantee, and the CHANGELOG says what changes for an existing consumer
- [ ] `npm run build`, `npm test`, `npm run typecheck`, `npm run eslint` (`--max-warnings 0`) and `npm run prettier:check` pass
