# Deliver a user's conversation list over the WebSocket protocol

Issue: re-cinq/HALEngine#144
Labels: type:feature, size:M, area:api, area:compliance, epic:extension-points

Part of #35

## Why

#143 gives a consumer `store.listFor(userId)`.
It does not give a **client** anything: the browser holding the socket cannot reach the store, so
every consumer that wants a history sidebar has to stand up its own authenticated HTTP route over
the same data the engine already authenticated on the upgrade. That is a second authorisation
path to the same personal data, written once per consumer, each one able to get the ownership
check wrong in its own way — the exact failure #45 went out of its way to avoid for resume.

A consumer may have no such route to extend: an engine deployment behind an api with a session
store and no conversation endpoints of its own has nothing to add this to. The engine already knows who is connected and already
replays a conversation on resume; answering "which conversations do I have" over the same socket
is the smaller surface.

## What to do

- `src/types/messages.ts`, additive only:
  - `ListConversationsMessage {type: 'list_conversations'; limit?: number; before?: string}` into
    `IncomingMessage`. There is no user id field, and that is the point: the list is always the
    connection's authenticated user's.
  - `ConversationListMessage {type: 'conversation_list'; conversations: ConversationSummary[]}`
    into `OutgoingMessage`, where `ConversationSummary` is `SessionSummary` with its two times as
    ISO strings — `Date` does not survive `JSON.stringify` as a `Date`, and the protocol types
    describe what goes on the wire.
- `validation.ts`: a `list_conversations` case — `limit`, when present, an integer 1–200;
  `before`, when present, a string `Date.parse` accepts. Anything else is `INVALID_MESSAGE`, as
  the two existing cases do it.
- Handling: `createMessageHandler` takes the session store and the new options alongside the
  orchestrator (`createServer` already holds both), and answers `list_conversations` on the
  non-locked path beside `ping` — a history request is not a turn and must not queue behind a
  streaming answer.
- The user id comes from `ws.userId`, never from the frame. Add the regression:
  a frame carrying an extra `userId` of another user is answered with the connecting user's own
  list.
- Opt-in: `HalEngineConfig.transport.history?: {enabled: boolean}`, default off, threaded through
  `createServer`'s options like `resume`. With it off, `list_conversations` is answered with an
  `error` frame and no list.
- A store that implements no `listFor` is answered with an `error`, not an empty list: a client
  that renders "no conversations" for a user who has several is a worse answer than one that
  renders a failure. `ErrorCodes` gains one code for both cases (`UNSUPPORTED`), additive.
- Picking a conversation needs nothing new: the client reconnects with `?sessionId=<id>`, which
  #45 already ships with the ownership check and the replay. No in-band switch frame, no second
  replay path.
- Specs and docs: extend `specs/hal-engine-websocket-protocol/spec.md` (the two frames, their
  field tables, the authorisation rule) and the conversation-list spec; add § Conversation list
  to `docs/getting-started.md` by editing `example/full-config.ts` and running `npm run docs:fix`
  — that listing sits under `<!-- doc-block: example/full-config.ts#full-config -->` and
  `npm run docs:check` fails a hand-edited block.

## Decisions

- **A frame, not a REST route.** The REST chat routes are demo-only and are not where a consumer is meant to build. The WebSocket is where the caller is
  already authenticated, once per connection, by the consumer's own `wsAuth`.
- **Its own opt-in flag, separate from `resume`.** Resume hands a client back a conversation it
  was already in; a list tells it what else the user has. A deployer who turned on resume did not
  thereby agree to the second disclosure, and a config that conflates them cannot be audited.
- **Answered off the per-session lock.** `PerSessionLock` serialises turns (#47). A list request
  that queued behind a two-minute streaming answer would look broken, and it mutates nothing.
- **An error, not an empty list, when it cannot be answered.** See above; silence that looks like
  data is the one failure mode a history view cannot recover from.
- **Answered when asked, never pushed.** No `conversation_list` arrives unsolicited: a client
  that just started a conversation knows, and a push would need a fan-out across the sockets a
  resumed session can be open on.
- **The frame is accepted by `validateMessage` whether or not the feature is on**, and the
  handler is what refuses it. Validation is static and has no config; the alternative is
  threading options into a pure validator to turn a type into "unknown".

## Acceptance criteria

- [ ] `src/types/messages.ts` gains only new interfaces and their two union members (**amended:** four interfaces, not two — each frame needs a type for its own payload, `ConversationCursor` for what a client sends back and `ConversationSummary` for a row on the wire) — a
      `git diff` of that file touches no existing line, and a fixture pins that every message
      literal valid before this change still compiles
- [ ] `validateMessage({type: 'list_conversations'})` is valid; with `limit: 0`, `limit: 201`,
      `limit: 1.5`, `limit: '10'` or `before: 'not a date'` it is invalid with a message naming
      the field
- [ ] With `history: {enabled: true}` and a store holding three conversations for the user, a
      `list_conversations` frame is answered with exactly one `conversation_list` carrying three
      summaries, newest first, each `createdAt` and `updatedAt` an ISO string, and no
      `stream_end`
- [ ] A frame carrying `{type: 'list_conversations', userId: '<another user>'}` is answered with
      the connecting user's own list, and the store's `listFor` is called with `ws.userId` —
      asserted on the recorded argument, not only on the frame
- [ ] `limit` and `before` reach `listFor` as the frame sent them. **Amended:** `before` is a
      `{updatedAt, sessionId}` cursor of ISO strings, not a `Date`. This was written before
      #143's review found that paging on a timestamp alone drops a conversation whenever two
      share an activity time, so the store's cursor became a composite that accepts an ISO
      string; a `Date` cannot carry the tie-break. The handler passes `{limit, before}` with
      both possibly `undefined` rather than omitting the argument, which is the same call
- [ ] With `history` absent, the same frame is answered with one `error` frame whose code is
      `UNSUPPORTED` and no `conversation_list`
- [ ] With `history: {enabled: true}` against a store implementing no `listFor`, the answer is
      the same `error` frame, and `grep` shows no code path that sends `conversations: []`
- [ ] A `listFor` that rejects is answered with one `error` frame whose code is `SERVER_ERROR`
      and whose message carries no store detail, the socket stays open, and the failure is
      logged with the session id and no user content. **Added during the build:** a store throwing
      the new exported `StoreCannotList` is answered `UNSUPPORTED` instead, so an injected
      collection without a `find` reads as the misconfiguration it is rather than a database
      that failed
- [ ] A `list_conversations` sent while a `user_message` is streaming on the same session is
      answered before that turn's `stream_end` — it does not wait on the lock
- [ ] A client that takes an id from a `conversation_list` and reconnects with `?sessionId=<id>`
      receives `resumed: true` and that conversation's replay, with no new transport code: the
      test exercises the existing #45 path end to end
- [ ] `ConnectedMessage` is unchanged by this issue
- [ ] **GDPR.** The protocol spec states that `conversation_list` carries one authenticated
      user's own conversation metadata and no conversation content, that the user id is taken
      from the connection and never from the frame, and that `transport.history` is the

- [ ] `CHANGELOG.md` carries an entry under `## [Unreleased]` written for somebody installing the

## Amendments

Three things changed between writing this issue and building it, each marked in the criterion it
affects:

1. **`before` is a cursor, not a timestamp.** #143's review found that paging on `updatedAt` alone
   silently drops a conversation when two share an activity time. The store's cursor became
   `{updatedAt, sessionId}`, so the frame carries both halves and the validator refuses one half
   alone. Built as originally written, the transport would have reintroduced the defect the store
   had just been fixed for.
2. **`messages.ts` gains four interfaces, not two** — the two frames plus the two payload types
   they describe.
3. **`StoreCannotList` is new public surface**, beyond what this issue specified: without it a
   permanent store misconfiguration cannot be told from a transient failure, in either the client
   frame or the log.

Two decisions the criteria did not anticipate:

- **`transport.history` without `transport.resume` is useless, and now says so.** `?sessionId=` is
  read only when resume is enabled, so a list whose rows cannot be opened is a deployment slip:
  the engine warns at startup and the documentation says so where it tells a client to reconnect
  with a row's id. Refusing to start was considered and rejected as too blunt for a library.
- **The conversation the connection is in is listed like any other**, so a fresh connect sees a row
  of its own holding no entries. Filtering it out was rejected: it is a real conversation the user
  is in, and it is their newest the moment they send anything.
