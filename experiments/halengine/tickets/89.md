# Let a Vertex deployment reach the EU multi-region endpoint

Issue: re-cinq/HALEngine#89
Labels: priority:high, type:feature, size:S, area:api, area:compliance

## Why

`VertexConfig` pins a deployment's inference region through `location`, and `vertexProvider.ts` passes it straight to `new VertexAI({project, location, googleAuthOptions})`. That covers every single Vertex region, and it is how a consumer keeps data in the EU today.

It no longer reaches the current models. Google does not serve the Gemini 3.x family from single European regions: `europe-west1`, `europe-north1` and the rest serve the 2.5 family only, while 3.x is available on the `global` endpoint and, since May 2026, on the `eu` multi-region. The 2.5 family retires on 2026-10-16. After that date a consumer who must keep inference in the EU has no model reachable through `location` at all, and the only remaining choices are `global`, which places the processing outside the EU, or no Gemini.

The `eu` multi-region is not a location string. It is a separate host, `aiplatform.eu.rep.googleapis.com`, and `@google-cloud/vertexai` builds its endpoint from `location` unless it is given one. So today a consumer cannot reach it through HAL Engine at all, no matter what they put in `location`.

This is blocking in `re-cinq/Otto`, which serves Danish OLT customers under a NIS-2 and GDPR residency obligation. Its model allowlist (`apps/api/src/configuration/models.ts`) refuses to start unless the running provider's region matches an assessed row, so "point it at `global`" is not a configuration edit there, it is a compliance decision. Otto is shipping `gemini-2.5-flash-lite` in `europe-west1` as a time-boxed stopgap that dies with the 2.5 retirement; this issue is the durable answer.

## What to do

One additive field on `VertexConfig` in `src/providers/vertex/vertexProvider.ts`, passed through to the SDK:

- Add `apiEndpoint?: string` to `VertexConfig`, documented as the base Vertex endpoint, naming the EU multi-region host as the case it exists for.
- Pass it to `new VertexAI({...})`. `VertexInit.apiEndpoint` already exists in `@google-cloud/vertexai` (checked against 1.12.0, peer range `^1.10.4`), so no SDK bump is needed.
- When it is absent, behaviour is byte-for-byte what it is today: the SDK derives the endpoint from `location`. The change is additive and the version bumps MINOR.
- `docs/providers.md`'s Vertex configuration example gains the field with one sentence on when a deployer needs it, and states that `location` alone cannot reach a multi-region endpoint.

The deployer-facing rule worth writing down once, in the docs rather than in code: `apiEndpoint` decides where the request goes, `location` decides what the request claims, and a mismatch between them is a residency bug that no type can catch.

## Tech notes

The mechanical change is small; it is high priority because of the date. Gemini 2.5 retires 2026-10-16 (2026-10-20 on the Agent Platform), and until this ships, every EU-resident HAL Engine consumer loses its model on that date with no configuration that recovers it.

Whether the `eu` multi-region actually serves a given model id is Google's answer, not this issue's: the field makes the endpoint reachable, it does not promise availability. A consumer still has to check before pinning a row.

Out of scope: choosing a model or a region for any consumer; Otto's allowlist row, which treats the region string as the assessed value and is `re-cinq/Otto`'s business; the `global` endpoint, which already works through `location` today; multi-region support for Bedrock; and any retry, failover or availability probing around an endpoint that does not serve a model.

Key files: `src/providers/vertex/vertexProvider.ts` (the `VertexConfig` type and the `new VertexAI` call), `src/providers/vertex/vertexProvider.test.ts` (SDK module mocking pattern), `docs/providers.md` (the Vertex configuration example). Verified against `@google-cloud/vertexai` 1.12.0: `VertexInit.apiEndpoint` is "the base Vertex AI endpoint to use for the request".
