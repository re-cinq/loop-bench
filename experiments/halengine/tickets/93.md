# Report usage across every tool round, not just the last

Issue: re-cinq/HALEngine#93
Labels: priority:medium, type:feature, size:S, area:api

## Why

`afterModelResponse` is the hook a deployer reaches for when they need to record what a turn cost — an audit entry, a billing line, a usage budget. It is called once per user message, after the round loop exits, and is handed the `lastUsage` local: `chatOrchestrator.ts` assigns `lastUsage = outcome.usage ?? lastUsage` on each round, so what the hook receives is the usage of the final provider call alone.

For a turn that answered directly, that is the whole turn. For a turn that called tools, it is the last leg of several, and the earlier rounds — including the one carrying the customer's question and the full tool results — are not counted anywhere. A deployer billing or budgeting from this hook under-counts exactly the expensive turns, and nothing in the signature hints at it. The current behaviour is recorded in `specs/hal-engine-config-hooks/spec.md` so it is at least discoverable, but documenting a surprising number is weaker than not producing one.

Raised by the reviewer on HALEngine#83, which recorded the behaviour but could not change it: that PR's ticket scoped itself to specifying the seam, not altering the orchestrator.

## What to do

Decide, and make the signature say the answer. Two shapes are worth weighing, and the issue should record why the other was rejected:

- Accumulate across rounds and pass the sum, keeping one `usage` argument. Simple for the common case, and it silently changes what an existing consumer records — the number gets larger for tool-heavy turns, which is the point, but it is a behaviour change worth a MINOR bump and a changelog line that says so.
- Pass both, for example the summed total plus the per-round breakdown, so a consumer that wants provider-call granularity keeps it. More faithful, wider surface.

Whichever is chosen, a turn that ran no tools must report exactly what it reports today, so the common path does not move.

## Acceptance criteria

- [ ] A turn driven through two tool rounds reports usage covering every provider call in that turn, asserted against a scripted provider whose rounds report known, different token counts
- [ ] A turn with no tool calls reports exactly what it reports today, pinned by the existing test remaining unedited
- [ ] A provider that reports no usage on some rounds does not make the total `undefined` or `NaN`: the rounds that reported are still counted, and a turn where nothing reported still reports nothing
- [ ] The type of what the hook receives makes the answer unambiguous, so a reader does not have to open the orchestrator to learn whether it is a sum
- [ ] `specs/hal-engine-config-hooks/spec.md` replaces its recorded under-counting line with the new behaviour, and the CHANGELOG entry states the change in what an existing consumer will record
- [ ] `npm run build`, `npm test`, `npm run typecheck`, `npm run eslint` (`--max-warnings 0`) and `npm run prettier:check` pass, with no `any` in the public API

## Tech notes

Out of scope: the audit entry or billing record itself, which is a consumer's concern; token accounting for anything other than the provider calls the orchestrator makes; and the `stop` chunk's own `usage` shape, which providers already populate and this issue only aggregates.

Key files: `src/orchestration/chatOrchestrator.ts` (the `lastUsage` local and the `afterModelResponse` call site), `src/types/ai.ts` (`UsageMetadata`), `specs/hal-engine-config-hooks/spec.md`.
